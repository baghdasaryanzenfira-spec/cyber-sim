## Քայլ 0 — Նախագծի վերլուծություն և պլանավորում (2026-10-06)

**Ռեպոզիտորիայի առկա վիճակը.** դատարկ IntelliJ Maven նախագիծ (`pom.xml`՝ `org.example:cyber-sim`-ով,
Java 21, առանց կախվածությունների, առանց ելակետային կոդի), որը git ռեպոզիտորիա չէր։ Պահպանելու ոչինչ չկար։

**Առկա միջավայրը.** JDK 21.0.4, Node.js 25.1, տեղադրված Docker Desktop (շարժիչը սկզբում գործարկված չէր),
գլոբալ տեղադրված Maven չկար։

**Նախագծի սեփականատիրոջ հետ համաձայնեցված որոշումներ՝**
- ԱԲ մատակարար՝ Claude API (անցանց աշխատանքի համար՝ փորձնական (mock) մատակարարով)։
- Փաստաթղթավորում անգլերենով (`docs/en`, հիմնական) և հայերենով (`docs/hy`, թարգմանություն)։
- LocalStack-ը ընդունելի է → ներառված է որպես Compose-ի ընտրովի պրոֆիլ, ոչ թե հիմնական կախվածություն։
- Սցենարներ՝ երեք ամենապարզերը — SSH brute-force, կասկածելի մուտք / վտանգված նույնականացման տվյալներ,
  հանրությանը բաց պահոցի bucket։
- Մոնոռեպոզիտորիա (monorepo)՝ `backend/`, `frontend/`, `docs/` պանակներով։

**Ստեղծված են.** 01–10 փաստաթղթերը (ընդհանուր նկարագիր, պահանջներ, տեխնոլոգիաների հետազոտություն,
ճարտարապետություն, տվյալների բազայի նախագծում, backend API-ի սահմաններ, frontend-ի կառուցվածք, սիմուլյացիայի
շարժիչի նախագծում, ԱԲ ինտեգրման ռազմավարություն, անվտանգություն)։

**Ինչու առաջինը.** ճարտարապետությունը, տվյալների մոդելը և API-ի պայմանագիրը որոշում են բոլոր հետագա փուլերը.
դրանք նախապես գրելը կանխում է վերամշակումը և ավարտական աշխատանքին վաղ տրամադրում է նախագծման գլուխը։

## Քայլ 1 — Ռեպոզիտորիայի/նախագծի կառուցվածք (2026-10-06)

**Իրականացված է՝**
- `git init` (`main` ճյուղ), արմատային `.gitignore` (անտեսում է `.env`-ը, կառուցման արդյունքները, IDE ֆայլերը)։
- Backend-ի կմախքը գեներացված է Spring Initializr-ով **Spring Boot 4.1.1**-ի համար (այդ պահին վերջին կայուն
  տարբերակը), Java 21, `am.cybersim` փաթեթ, Maven wrapper — կախվածություններ՝ Web MVC, Security, Data JPA,
  Validation, PostgreSQL, Flyway, Actuator, Testcontainers։
- Հեռացված է սկզբնական դատարկ արմատային `pom.xml`-ը (սեփականատիրոջ համաձայնությամբ). backend-ն այժմ գտնվում է
  `backend/`-ում։
- `frontend/`, `docs/en/`, `docs/hy/` պանակներ։

**Ինչու Spring Initializr.** այն ստեղծում է starter-ների համահունչ, տարբերակներով համաձայնեցված հավաքածու։
Spring Boot 4-ը starter-ները բաժանել է ավելի փոքր մոդուլների (օրինակ՝ `spring-boot-starter-webmvc`,
`spring-boot-starter-flyway` և համապատասխան `*-test` starter-ներ). POM-ի գեներացումը վերացնում է նոր
արտեֆակտների անունները գուշակելու անհրաժեշտությունը։

**Ինչու Maven wrapper.** Maven-ը գլոբալ տեղադրված չէ. `mvnw`-ն ներբեռնում է ամրագրված Maven տարբերակը, ուստի
յուրաքանչյուր մշակող և Docker-ի կառուցումը օգտագործում են կառուցման նույն գործիքը։

## Քայլ 2 — Տվյալների բազա և backend-ի հիմք (2026-10-06)

**Իրականացված է՝**
- `V1__initial_schema.sql` — բոլոր մոդուլների ամբողջական սխեման (օգտատերեր, սցենարների ձևանմուշներ,
  սիմուլյացիաների նմուշներ, արդյունքներ, ԱԲ աուդիտի մատյան)՝ CHECK սահմանափակումներով, եզակի բանալիներով,
  ինդեքսներով և **մասնակի եզակի ինդեքսով** (partial unique index), որը յուրաքանչյուր ուսանողի և սցենարի համար
  թույլ է տալիս միայն մեկ չավարտված սիմուլյացիա։
- `application.yml` — միջավայրից կախված յուրաքանչյուր արժեք կարդացվում է միջավայրի փոփոխականներից.
  `ddl-auto: validate` (սխեման կառավարում է Flyway-ը, Hibernate-ը միայն ստուգում է, որ էնտիտիները համապատասխանում
  են դրան). `open-in-view: false`։
- `AppProperties` — տիպավորված կոնֆիգուրացիայի record (`app.jwt`, `app.cors`, `app.demo`, `app.ai`,
  `app.scenarios`)։
- `common/ApiError`, `ApiException`, `GlobalExceptionHandler` — սխալների մեկ ձևաչափ բոլոր endpoint-ների համար։
- `ClockConfig` (ներարկվող ժամացույց՝ ժամանակի տրամաբանությունը թեստավորելի դարձնելու համար), `OpenApiConfig`
  (Swagger՝ bearer նույնականացմամբ)։

**Ինչու ամբողջ սխեման V1-ում.** տվյալների մոդելն ամբողջությամբ նախագծվել էր 0-րդ փուլում. մեկ վերանայված
միգրացիան ավելի հեշտ է ներկայացնել ավարտական աշխատանքում, քան բազմաթիվ փոքր միգրացիաներ։ Հետագա
փոփոխությունները կլինեն նոր միգրացիաներ (`V2__...`), այլ ոչ թե V1-ի խմբագրումներ։

**Ինչու `open-in-view: false`.** կանխում է ծույլ բեռնումը (lazy loading) JSON-ի ձևավորման ընթացքում. պատասխանի
համար անհրաժեշտ բոլոր տվյալները պետք է բեռնվեն ծառայության տրանզակցիայի ներսում, ինչը հարցումները դարձնում է
բացահայտ և կանխում N+1 անակնկալները։

## Քայլ 3 — Նույնականացում և թույլտվությունների կառավարում (2026-10-06)

**Իրականացված է՝**
- `User` էնտիտի, `Role` enum (`STUDENT`, `ADMIN`), `UserRepository`, `UserDto`։
- `JwtConfig` — HS256 բանալի `JWT_SECRET`-ից (≥ 32 բայթ, հակառակ դեպքում գործարկումը ձախողվում է. մշակման
  միջավայրում, եթե սահմանված չէ, օգտագործվում է պատահական բանալի՝ նախազգուշացմամբ), `NimbusJwtEncoder` /
  `NimbusJwtDecoder`՝ թողարկողի (issuer) վավերացմամբ։
- `JwtTokenService` — թողարկում է թոքեններ՝ `sub`, `email`, `name`, `role`, `iss`, `iat`, `exp` դաշտերով։
- `SecurityConfig` — վիճակ չպահող ֆիլտրերի շղթա, URL կանոններ (`/api/admin/**` → ADMIN), role claim → `ROLE_*`
  իրավասություններ (authorities), CORS, JSON 401/403 պատասխաններ, BCrypt գաղտնաբառերի պատվիրակող կոդավորիչ։
- `AuthUser` + `AuthUserArgumentResolver` — կոնտրոլերները նույնականացված օգտատիրոջն ստանում են որպես պարամետր։
- `AuthService` / `AuthController` — `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`։
- `DemoDataInitializer` — միջավայրի փոփոխականներից ստեղծվող ընտրովի ցուցադրական ադմինիստրատոր/ուսանող։

**Ծագած խնդիրներ՝**
- Spring Boot 4-ը թեստային անոտացիաները տեղափոխել է նոր մոդուլներ/փաթեթներ
  (օրինակ՝ `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc`) և օգտագործում է Jackson 3
  (`tools.jackson.databind`)։ Լուծում. դասերը գտնվել են ներբեռնված jar ֆայլերում՝ գուշակելու փոխարեն։

**Անվտանգության մանրամասներ, որոնք արժե նշել ավարտական աշխատանքում՝**
- Նույն սխալը անհայտ էլ. փոստի / սխալ գաղտնաբառի / անջատված հաշվի դեպքում, ինչպես նաև անհայտ էլ. փոստերի համար
  կեղծ BCrypt ստուգում (ժամանակի հավասարեցում) → օգտատերերի թվարկում (user enumeration) հնարավոր չէ։
- Գրանցման DTO-ն չունի `role` դաշտ, ուստի `ADMIN` դերի զանգվածային վերագրումը (mass assignment) անհնար է
  (թեստավորված)։
- Հարցումների DTO-ների `toString()`-ը քողարկում է գաղտնաբառերը, ուստի դրանք երբեք չեն հայտնվում լոգերում։

**Թեստավորում.** `AuthIntegrationTest` — 10 թեստ իրական PostgreSQL 17-ի նկատմամբ (Testcontainers)՝
գրանցում, դերի ընդլայնման փորձ, կրկնվող էլ. փոստ (մեծատառ/փոքրատառ անտարբեր), վավերացման սխալներ, մուտք,
`/me`՝ թոքենով, սխալ գաղտնաբառ՝ անհայտ էլ. փոստի համեմատ, անջատված հաշիվ, բացակայող թոքեն → JSON 401,
կեղծված թոքեն → 401։ **TESTED (թեստավորված). 10/10 հաջողված** (`mvnw test`, 2026-10-06)։

## Քայլ 4 — Սցենարների կառավարում (2026-10-06)

**Իրականացված է.** սցենարի էնտիտիներ (`Scenario` + նպատակներ, ռեսուրսներ, իրադարձություններ, գործողություններ,
հուշումներ), `ScenarioDefinition` (յուրաքանչյուր սցենարի համար մեկ JSON փաստաթուղթ), `ScenarioDefinitionValidator`
(խաչաձև հղումների կանոններ), `ScenarioMapper`, `ScenarioService`, ուսանողական կատալոգի endpoint-ներ,

**Ինչու մեկ փաստաթուղթ սկզբնական տվյալների ֆայլերի, ադմինիստրատորի խմբագրիչի և ԱԲ ելքի համար.** մեկ
վավերացնողը պաշտպանում է մուտքի բոլոր երեք կետերը. տե՛ս ADR-5։

**Ծագած խնդիրներ՝**
- Hibernate-ը ներդրումները (insert) կատարում է որբ գրառումների ջնջումից (orphan delete) առաջ, ուստի նույն
  բանալիներով դուստր տարրերի փոխարինումը խախտում էր եզակիության սահմանափակումները։ *Լուծում.* մաքրել
  հավաքածուները և կատարել `flush()` նոր դուստր տարրերն ավելացնելուց առաջ (`ScenarioService.update`)։
- Միավորային թեստերում օգտագործվում էին մեկտառանի գործողությունների բանալիներ, որոնք մերժվում էին բանալու
  ձևանմուշով (pattern). խաչաձև հղումների կանոններին երբեք չէր հասնում։ *Լուծում.* թեստերում իրատեսական
  բանալիներ (վավերացնողը ճիշտ էր)։

**Թեստավորում.** `ScenarioDefinitionValidatorTest` (9 միավորային թեստ), `ScenarioCatalogIntegrationTest` (5) —
ներառում է ստուգում, որ ներածական տեղեկանքի JSON-ը լուծման վերաբերյալ տվյալներ չի պարունակում։ **TESTED.**

## Քայլ 5 — Սիմուլյացիայի շարժիչ (2026-10-06)

**Իրականացված է.** `SimulationStatus`, `SimulationStateMachine` (անցումների մաքուր ֆունկցիաներ), էնտիտիներ՝
`Simulation`, `SimulationResource`, `SimulationEvent`, `SimulationAction`, `SimulationResult`. `SimulationEngine`

**Հիմնական որոշումներ՝**
- *Շարժիչ՝ առանց պահպանման (persistence) տրամաբանության.* շարժիչը միայն փոփոխում է ագրեգատը, իսկ ծառայությունը
  կառավարում է տրանզակցիաները և սեփականության ստուգումները → շարժիչը միավորային թեստավորվում է առանց տվյալների
  բազայի (`SimulationEngineTest`)։
- *Գործողությունների պատկերներ (snapshots).* պիտակը, ելքը և միավորները պատճենվում են `simulation_actions`-ում,
  ուստի պատմությունը կայուն է։
- *Լավատեսական արգելափակում* (optimistic locking, `lock_version`) `simulations`-ի վրա՝ պաշտպանում է կրկնակի
  սեղմումներից/զուգահեռ հարցումներից։
- *Տեղեկատվության թաքցում.* ուսանողական DTO-ները մինչև ավարտը ելքի/միավորների/ապացույցների համար պարունակում են
  `null`։
- *Մասնակի եզակի ինդեքսը* երաշխավորում է յուրաքանչյուր ուսանողի և սցենարի համար առավելագույնը մեկ չավարտված փորձ։

**Ծագած խնդիր.** `complete()`-ը կանչում էր `@Transactional` `result()` մեթոդը `this`-ի վրա. Spring-ի պրոքսին
շրջանցվում էր, և ծույլ բեռնվող սցենարը չէր բեռնվում (`LazyInitializationException`)։ *Լուծում.* այդ քայլի համար
բացահայտ `TransactionTemplate` (փաստաթղթավորված է կոդում)։

**Թեստավորում.** `SimulationStateMachineTest` (15), `SimulationEngineTest` (8), `SimulationFlowIntegrationTest` (7 —
անթերի անցում = 100, սխալներով անցում = ճիշտ 13 միավոր՝ ինչպես ձեռքով հաշվարկված էր, անվավեր անցումներ = 409,

  ապացույցների վահանակով, ԱԲ օգնական, գործողությունների կատալոգ՝ հաստատման երկխոսության պատուհանով, միջադեպի
  ժամանակագրություն, ավարտ/հրաժարում), արդյունք (միավորների ցուցիչ, ԱԲ հետադարձ կապ, մանրամասն բաշխում,
  բաց թողնված գործողություններ, ապացույցներ, բացատրություն), առաջընթաց և պատմություն (թեմաների գծապատկեր, ԱԲ
  առաջարկություններ)։
- Ադմինիստրատորի էջեր՝ վահանակ, օգտատերեր (միացում/անջատում, առաջընթաց), սցենարներ (ակտիվացում, ԱԲ տարբերակ),
  **սցենարների խմբագրիչ** (General / Infrastructure / Logs & evidence / Actions & scoring / Hints / JSON
  ներդիրներ, տողերի խմբագրման ընդհանուր երկխոսության պատուհան, backend-ից ստացվող վավերացման սխալներ), փորձեր
  (ֆիլտրեր, էջավորում, մանրամասներ՝ ԱԲ փոխազդեցություններով), վերլուծություն։

**Ինչու գրադարանների նորագույն հիմնական տարբերակները (Vite 8, MUI 9, React Router 8).** դրանք ընթացիկ կայուն
թողարկումներն էին. պաշտոնական ձևանմուշի և TypeScript կոմպիլյատորի՝ որպես անվտանգության ցանցի օգտագործումը
(ուղղվել է ընդամենը երեք տիպային սխալ) վերացրեց նոր API-ները գուշակելու անհրաժեշտությունը։

**Chrome-ում ձեռքով ստուգման ընթացքում հայտնաբերված խնդիրներ (բոլորն ուղղված են)՝**
1. *Վթար հուշում պահանջելուց հետո* ("l is not a function")։ Պատճառ. `useEffect(() => el.scrollIntoView({behavior:'smooth'}))`
   էֆեկտը վերադարձնում էր `scrollIntoView`-ի արժեքը. արդի Chrome-ը սահուն ոլորման դեպքում վերադարձնում է Promise,
   որը React-ը փորձում էր կանչել որպես էֆեկտի մաքրման (clean-up) ֆունկցիա։ Ուղղում. բլոկային մարմնով էֆեկտ։ Դաս.
   էֆեկտները երբեք չպետք է օգտագործեն արտահայտության տեսքով մարմին։
2. *Ադմինիստրատորի տողերի խմբագրիչը կորցնում էր մուտքագրված տեքստը* — երկխոսության պատուհանը վերասկզբնավորվում
   էր ծնող բաղադրիչի յուրաքանչյուր ռենդերի ժամանակ, քանի որ ամեն անգամ ստեղծվում էին նոր լռելյայն օբյեկտ և դաշտերի
   ցանկ։ Ուղղում. խմբագրվող տողը պահվում է վիճակում (state) պատուհանը բացելիս։
3. *Սիմուլյացիայի նեղվածք եռասյուն դասավորություն ~1150 px լայնության դեպքում* — երեք սյունակ այժմ միայն `xl`
   սահմանակետից (breakpoint) սկսած, լոգերի տողերը օգտագործում են երկտողանի դասավորություն։
4. Մեկ կետով միավորների գծապատկերը՝ առանց նշիչի. ադմինիստրատորը մուտքից հետո վերահղվում էր `/`, այլ ոչ թե
   `/admin`. backend-ի վերագործարկման ընթացքում ցանցային սխալների դեպքում թոքենը ջնջվում էր։ Բոլորն ուղղված են։
5. `index.html`-ը PowerShell հրամանով պահպանվել էր սխալ կոդավորմամբ, ինչը խափանեց Vite-ի կառուցումը ("stream did
   not contain valid UTF-8"). ֆայլը վերագրվել է UTF-8-ով։

**Թեստավորում.** `npm run build` (տիպերի ստուգում + արտադրական կառուցում) հաջողվում է։ Միջերեսի ձեռքով ստուգում
Chrome-ում՝ մուտք, վահանակ, սցենարներ, ներածական տեղեկանք, մեկնարկ, գործողություն, ապացույցներ/լոգեր, հուշում,
ավարտ, արդյունք, ադմինիստրատորի վահանակ, սցենարների ցանկ, խմբագրիչ, վերլուծություն — **VERIFIED (ստուգված)**։
